# Model-directed slide generation

The pitch frontend offers the standard narrative/design generator and, after local installation, the specialist AutoPresent slide model. Neither path executes model-generated Python.

1. The saved project context supplies the founder's idea, reviewed claims, source references, exact figures and open questions.
2. The model selects one theme and a varied set of compositions, writes short topic-specific points and speaker notes, and supplies comparison/group headings. Slides are authored in batches of three to fit the local output budget.
3. Strict JSON validation checks IDs, shapes and content limits. Original evidence and statistics are merged from the saved context instead of being regenerated by the model. Missing market information remains a gap; it does not block generation.
4. A renderer produces native editable PowerPoint text, diagrams and tables in widescreen format. Dense original excerpts remain complete in speaker notes, with a visible note where details have been shortened for readability. Slide count remains the requested count.
5. The existing frontend buttons create, preview, edit and download the resulting artifact. Saved legacy decks keep their previous renderer.

Reports use the same output author for eight narrative sections, retaining the formal layout, immutable research sections and source bibliography. Posters keep their existing generation path.

## Model configuration

`OUTPUT_LLM_MODEL` selects a dedicated writer/design model. Leave it empty to reuse the server's `LLM_MODEL` (Qwen3 4B on this installation). The research/debate dropdown continues to control those research workflows. `OUTPUT_NUM_PREDICT`, `OUTPUT_TEMPERATURE` and `OUTPUT_TIMEOUT` control export authoring independently. No new model weights are required for this design engine.

## AutoPresent integration

The **Slide generator** selector in Pitch and Visual Studio switches between the standard generator and **AutoPresent · Llama 3.1 8B (experimental)**. AutoPresent designs the geometry and styling itself instead of choosing an application layout template. Its text comes from the saved project's grounded content; reports and research keep their existing models.

Install once from `member1/backend` using PowerShell:

```powershell
.venv\Scripts\python.exe scripts\setup_autopresent.py setup
```

Setup automatically creates `.runtime/autopresent/conversion-venv`, installs its pinned download dependencies from `requirements-autopresent-setup.txt`, and continues inside that environment. It requires no Hugging Face packages in the application's `.venv`. Subsequent setup runs reuse the environment and resume verified downloads. `start`, `stop`, and `status` do not install packages.

The installer downloads the official [AutoPresent detailed-instruction LoRA](https://huggingface.co/JiaxinGe/llama-3.1-8b-autopresent_detailed_instruction), the exact Llama 3.1 8B Instruct base in Q4_K_M form, and a pinned official llama.cpp runtime/converter. It fetches only the converter's required Llama modules and GGUF package files, avoiding the large full-repository source archive. Every source file is verified against its Git blob hash from the pinned official tree, with a per-file SHA-256 recorded for provenance. Source revisions, publisher checksums and conversion provenance are saved in ignored `models/autopresent/manifest.json`. The full base is not merged into a second copy, and a separate CPU-only conversion environment avoids changing the application's dependencies. Allow roughly 8 GB for model/runtime files plus conversion dependencies.

For each slide the real adapter generates a Python slide program, following its original training interface. A restricted AST interpreter translates supported Python-pptx operations and AutoPresent's `add_title`/`add_text` helpers to typed native objects. Safe function wrappers are interpreted symbolically; imports, save calls and generated Python are never executed. Common 10-inch and widescreen source canvases are normalized to the app's widescreen export, with room for its source footer.

AutoPresent controls layout, never the exported wording. The app binds each text box to the saved title or body blocks, grouping points when the model uses a shared text area. Model rewrites and invented claims are discarded. All source blocks must remain covered, and only canonical saved text reaches the renderer. Validation checks bounds, coverage, readable fonts and contrast; one layout repair is allowed before reporting an explicit generation failure. There is no hidden fallback to a generic model. The final PPTX retains source links and complete evidence in notes and stays editable.

The app unloads its configured Ollama writer, starts the separate server at `127.0.0.1:8091`, and stops it after the deck completes or fails. AutoPresent and all app-managed Ollama writers share a GPU lock, so another local model request waits until slide generation has stopped and released memory. The Shutdown button also stops a verified owned AutoPresent process. The default uses partial GPU offload for the 6 GB laptop GPU; generation can be slower than the smaller text model. Start with five slides. `AUTOPRESENT_TIMEOUT` controls each slide request. `scripts/setup_autopresent.py status`, `start`, and `stop` provide local diagnostics without downloading assets.

The matching base GGUF comes from Ollama's official `llama3.1:8b-instruct-q4_K_M` registry blob, pinned by SHA-256. On connections where Hugging Face transfers stall, set `AUTOPRESENT_HF_MIRROR=https://hf-mirror.com` for setup; the adapter is still checked against the official release's exact size and SHA-256. Downloads resume from completed byte ranges and verify the whole-file checksum before use. Runtime defaults to 30 GPU layers, Flash Attention and a quantized KV cache to fit this laptop; `start --gpu-layers 20` can reduce GPU usage.

## Other slide-generation approaches considered

| System | Capability | Fit for this application |
|---|---|---|
| [Open WebUI Generate Slides](https://github.com/ianustec/openwebui-generate-slides) | Model JSON drives editable slide layouts and shapes | A similar design-plan architecture; its Open WebUI wrapper requires adaptation. We implement the plan within the existing app. |
| [Presenton](https://github.com/presenton/presenton) | Full presentation engine with Ollama and editable PPTX output | A possible larger rendering replacement; introduces a separate application and runtime. |
| [PPTAgent / DeepPresenter](https://github.com/icip-cas/PPTAgent) | Presentation planning, coding and visual revision; a specialized model is available | A full agent/tool workflow, rather than a proven drop-in writer. Current setup requires additional platform and rendering tools. |
| [AutoPresent](https://github.com/para-lost/AutoPresent) | A Llama-based slide-code model | Integrated as a separate optional generator with static translation of its actual program output. |

The other alternatives were assessed from primary documentation and have not been benchmarked locally. The two implemented paths are AI-selected application layouts and AutoPresent-generated geometry, both compiled to native editable PowerPoint objects.
